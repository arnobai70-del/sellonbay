# Decisions

Short record of rules chosen while building. Newest at the bottom. Change a rule here and in CLAUDE.md together.

## File release (decided 2026-10-08, from the spec)
- The buyer gets the seller's real files as soon as the order is funded (money in escrow), not only after Accept. Never before payment, never public.
- Delivery is a signed link to our own download route (HMAC, 24 hours, `DELIVERY_TTL_SECONDS` to change), not the seller's own link. The buyer can request a new link any time, at most 5 an hour per order. Downloads are also limited per IP (30 an hour).
- One licence key per order (`licenses`), created the first time it is needed.
- Every download is logged in `download_events` (user, time, IP, user agent, SHA-256 of the file, bytes). The table is append-only: a trigger blocks update, delete and truncate even for the server.
- The seller's link is fetched by the server and streamed to the buyer, only over https and only to public addresses (SSRF guard); files over 500 MB are refused.
- Seller protection stays: escrow, 7-day hold before payout, disputes with evidence, and an optional release delay for new or high-risk buyers. The delay switches (`RELEASE_DELAY_MINUTES`, `RELEASE_DELAY_NEW_BUYER_DAYS`, `RELEASE_DELAY_HIGH_PRICE_CENTS`) are all off by default.
- Known limits: the rate limiter is in memory (use Redis or Upstash with several servers); files are streamed through our server, so very large files should move to storage with signed storage URLs; real orders are not created by the app yet (payments are demo), so the real-order route is covered by tests with rows made directly in the database.

## Pre-sale questions (decided 2026-10-08)
- A buyer can ask a seller a question before buying, on every product page (`POST /api/presale`). Signed-in only (in demo mode, with no accounts, a stand-in made from the connection).
- Same server-side chat filter as order chat (`lib/chatFilter.ts`): emails (also "name at gmail dot com", spaced-out letters, invisible characters), phone numbers (also spelled-out digits and full-width digits), other contact channels (WhatsApp, Telegram and so on), links, and paying outside SellOnBay. Plain product questions are allowed ("works with Gmail?", "can I take payments with PayPal?"). The buyer only sees a generic refusal, never which rule matched.
- Order of checks: hidden-field trap (silently dropped), a form sent in under 1.5 seconds is refused, signed in, Turnstile, rate limits, listing exists, daily caps, then the filter.
- Limits: 5 questions per 10 minutes per person, 10 per 10 minutes per IP address, 5 a day from one buyer to one seller, 20 a day per buyer. Blocked attempts count toward the daily caps. Limits are in memory, per server; use Redis or Upstash with several servers.
- Turnstile: set `TURNSTILE_SECRET_KEY` and `NEXT_PUBLIC_TURNSTILE_SITE_KEY`. Without them Cloudflare's TEST keys are used, which pass for everybody. They are NOT a bot check, so real keys are a launch blocker.
- Blocked attempts are stored in `blocked_messages` with the text, the reason, where it happened (`presale`, `presale_reply`, `order`), the listing and the IP, and shown to admins in "Blocked messages" on the admin dashboard. Sent questions are in `presale_messages`. Sellers see and answer them on their dashboard; the reply goes through the same filter.
- The made-up starter listings have no real seller, so questions about them are stored with no seller and nobody can answer them.

## Environment
`DELIVERY_SECRET` (signing key for download links; without it one is derived from the Supabase service key), `DELIVERY_TTL_SECONDS` (default 86400), `RELEASE_DELAY_MINUTES`, `RELEASE_DELAY_NEW_BUYER_DAYS`, `RELEASE_DELAY_HIGH_PRICE_CENTS` (all 0 = off), `TURNSTILE_SECRET_KEY`, `NEXT_PUBLIC_TURNSTILE_SITE_KEY`.

## Listing rules: drafts are soft, submit is strict (decided 2026-10-08)
- "Save draft" only needs a name. A draft is a `products` row with status `draft`: text fields only (files are not kept, the seller adds screenshots and the zip again when submitting). Drafts are never public. The seller reopens one from the dashboard (`/sell/new?draft=slug`); submitting from a draft removes it.
- "Submit for review" is refused (422, with a `missing` list and one readable sentence) until: a name (3 to 60 characters), a category, a description of at least 20 characters, at least 1 item under "What is included", a private link to the files or code (https), for websites a zip or a live demo link, for apps and digital products at least 1 screenshot (up to 6; 3 or more is recommended and shown in the strength meter), for digital products the tick that the files are clean and the seller's own, and a demo link for Plugins, Scripts, AI automations and Chatbots. The same function (`lib/listingRules.ts`) runs in the form and on the server; the server is the one that enforces it.
- This lowers the old rule of 3 to 6 screenshots for apps to 1 to 6, as the spec says.

## Trial copy, free sample, demo ranking
- Free sample: optional public https link on digital listings (on by default, `FEATURE_FREE_SAMPLE=0` turns it off). Shown as a "Free sample" link with `rel="nofollow"`. Admin reviews it with the listing. Show a taste, never the full product.
- Limited trial copy: OFF by default (`FEATURE_TRIAL_COPY=1` turns it on) because it needs the owner's decision. It is a SEPARATE cut-down file the seller uploads (zip, pdf, txt, md, json, csv, max 25 MB, stored privately at `trial/<product id>/`); we never trim the real file. Only for code and automation categories (`NEEDS_DEMO`), never for your own listing. Signed-in buyer, 1 trial per product per 7 days (max 3 requests a day), one-hour signed link, every download logged with kind `trial` (order_id holds the product id). The seller supplies a cut-down version, never the full file.
- Demo ranking: listings with a demo, sample, trial, screenshots, a real description and a "what's included" list get a small lift in browse (`lib/demoQuality.ts`, max +0.4 on the rating scale), so strong reviews still win. Off with `NEXT_PUBLIC_FEATURE_DEMO_RANKING=0`. Cards with a demo or sample show a "Demo included" badge.

## Orders, ledger and payments, built against fake providers (October 2026, spec phases 2 to 3 in part)
- **One place for numbers**: `lib/config.ts` (rules, with `tests/unit/config.test.ts`), `lib/brand.ts` (the name). Every API input is checked with Zod first (`lib/schemas.ts`, `lib/validate.ts`).
- **Orders** are rows in `orders` (migration 0015) with the spec's states (`draft`, `awaiting_payment`, `funded`, `in_delivery`, `delivered`, `accepted`, `payout_pending`, `paid_out`, `disputed`, `fix_requested`, `overdue`, `refunded`, `cancelled`). The legal moves are one table in `lib/orders/machine.ts`, tested move by move. Every change writes an `order_events` row (who, when, from, to, metadata), applied together with the change by the database function `order_apply` (an order that changed under you is refused, not overwritten). `order_events` cannot be edited or deleted. Without Supabase, or before the migration, orders are kept in memory with the same rules.
- **Time-based steps** are not derived any more. `runDueJobs` (route `POST /api/cron/orders`, secret `CRON_SECRET`, also run lazily when an order is read) does: auto-accept at the end of the 48-hour window, `overdue` at the deadline, `payout_pending` after the 7-day hold. Each step is dated when it became due, so an order left alone for a week still gets the right dates. The old SQL `accept_order` and its pg_cron job are removed so the numbers stay in `lib/config.ts`.
- **Demo seller**: made-up starter listings have no seller account, so a pretend seller starts after 8 seconds and delivers after about a minute (never replaces a real seller). "Demo controls" in the order page jump ahead. They go before the first real payment.
- **Ledger** (`lib/ledger.ts`, migration 0016, `ledger_post` function): double entry, whole cents, every entry balances, escrow and seller balances can never go below zero, each business event has a key (`pay:<order>`, `accept:<order>`, `hold:<order>`, `refund:<order>:full`, `extra:<request>`, `extra-accept:<request>`) so posting twice does nothing, rows are append-only. The old unused `wallets` table is removed: balances are sums over the ledger (`ledger_balances`). Extras (domains, hosting) are paid into escrow too and go to platform revenue on acceptance; the fee is taken on the first line (the product or package).
- **Payments**: `PaymentProvider` (`lib/providers/payment`), only `FakePaymentProvider` exists (test cards only). Provider events come in at `POST /api/webhooks/payment`: signature (HMAC) and age (5 minutes) checked, each event id processed once (`webhook_events`), a payment for the wrong amount or an unknown order is rejected, a refund on an accepted order is ignored (a dispute decides that). `PAYMENT_WEBHOOK_SECRET` has no default in production. The demo pay form sends its event through the same handler. D1 is still open.
- **Delivery types**: `live_site`, `download` and `repo_access` (the spec's three). Apps and installers count as `download`. Repository orders: the seller says the GitHub invite was sent, the buyer confirms they can open it, then the review window starts. Starter products `seo-audit`, `support-bot`, `wp-booking` use it; sellers choose it for digital products.
- **Licences**: `single_project`, `multi_project`, `full_transfer` per product, plus a third-party code declaration (MIT, Apache-2.0, GPL and others). Licences with conditions (GPL, LGPL, AGPL, MPL) show a visible note on the listing and on the certificate. All texts are tagged for lawyer review.
- **Extra work**: seller request (title up to 80 characters through the chat filter, from $5, 1 to 3 days, at most 3 waiting). The buyer approves and pays it into escrow (or declines, nothing charged); only then does the deadline move out. The fee is the flat 20% custom-work fee, taken from the seller's side at acceptance. Allowed while the order is open and not accepted.
- **Trial credit**: a trial costs at most $150 and lasts 3 to 5 days (`trialOf`). If the developer switched on "credit the trial fee" and the buyer accepted a trial, a full custom order with that developer within 30 days has the trial price taken off. Each trial is credited once (a unique index), and a cancelled order frees it. The credit never takes the price below $5.
- **Handover certificate** (`lib/certificate.ts`): a PDF made once when an order is accepted (order, product and version, parties, licence and its plain terms, UTC time, SHA-256 of every delivered file from the download log, history). Stored in the private `certificates` bucket (or memory), never changed (`certificates` table), downloadable by the buyer. Product version is always "1" until products have versions.
- **Where the code differs from the spec on purpose**: routes (`/product/[id]`), fonts and the home hero (owner's choice), starter trial price rule (a third of Basic, rounded, capped at $150), dispute reasons are still the older list (`not_as_described, does_not_work, malware, copyright, bug_fix`; the spec says `not_working` and `other`; the dispute flow is a later phase), `order_events` columns are `event, from_state, to_state, meta`, the ledger is one table of lines per entry key instead of `ledger_accounts` plus entries.
- **Not built yet** (later phases, waiting for the owner): real payments and payouts (D1), payout CSV export, dispute flow and admin screens, KYC (D4), real registrar (D3), deployment (D5), AI features, notifications and email, malware scan, Cloudflare and the rest of the security checklist, SEO files per category.

## Disputes, strikes, notifications, admin, security (October 2026)
- **Disputes** (migration 0019, `lib/disputes.ts`): spec reasons (`not_as_described, not_working, malware, copyright, other`; the old two were renamed), opened by the buyer only through the server, in the review window or the 7 days after accepting, one at a time per order. Evidence needs a real description (20+ characters) and goes through the chat filter (links are blocked too). Clocks: seller 48 hours, admin 5 days (shown as "late" in the queue, no automatic decision). Decisions: refund in full (from escrow, or by reversing the release if it was already accepted), partial refund (comes out of the seller's share, never more than the seller earns on the order), fix requested (the order goes back to the seller and a fresh review window opens), release (dispute rejected, seller paid as normal, a strike for the buyer; three flag the account through a database trigger).
- **Chat strikes** (`lib/strikes.ts`, migration 0020): 3 blocked messages in 30 days: warning (notification and email); 5: the account is suspended for 7 days (`profiles.suspended_until`), the admins are alerted, and every step is in `account_actions`. A suspended account is treated like a banned one everywhere (`lib/accounts.ts cannotAct`, the proxy, every API route that checked `banned`). Only blocked pre-sale questions exist as server chat today; the order chat is not built, but it will call the same `saveBlocked`.
- **Notifications** (`lib/notify.ts`, `emails/templates.ts`, `/notifications`): one `notify()` for every event in the spec: funded, due soon (6 hours before), delivered, review ending (12 hours before), accepted, overdue, extra work, dispute events, payout sent, listing decisions, chat warning, suspension, admin alerts. A reminder goes out once (dedupe key). Email goes through `lib/providers/email` (fake until the owner chooses Resend or Brevo and gives a key); domain-expiring has its template but no job yet (no real registrar).
- **Payouts** (`lib/payouts.ts`, migration 0021): weekly (Sunday) batch per seller from orders whose hold ended and that are in no payout yet; sellers without payout details are skipped and listed. CSV export locks the batch; an admin marks each payout paid with the transfer reference, which posts the ledger entry and moves the orders to `paid_out`. Money is sent by hand (Payoneer, Wise or bank). CSV cells that start with `= + - @` are neutralised.
- **Admin** (`/dashboard/admin/*`): review queue for listings and developer profiles (a digital product cannot be approved without the sandbox tick), disputes, payouts, accounts (ban, unban, lift suspension, clear flag, each with a reason), abuse reports (suspend pauses the listing), audit log (`audit_log`, append-only). Every admin route needs: signed in, role admin, not banned or suspended, authenticator code (aal2); demo mode has no accounts and lets everything through.
- **Security**: headers on every page and API answer except `/demo` (CSP without wildcard scripts or eval, HSTS, nosniff, frame options, referrer policy, permissions policy); `scripts/check-bundle.mjs` and `tests/unit/secrets.test.ts` keep every secret out of the browser bundle; Zod is not imported by client components (it probes for eval). Scripts and styles still allow 'unsafe-inline'.
- **Ledger shape**: `ledger_entries(entry_id, account, order_id, amount_cents, direction, memo)` plus `ledger_accounts`, as the spec says (migration 0018 renames the columns of 0016).
- Migrations to apply, in order: 0015 to 0021. The code now needs all of them (it reads `profiles.suspended_until`, for example).

## The rest of the spec's list (October 2026)
- **Express delivery** (migration 0022): a seller offers 24-hour express for $10 to $20 (limits in `lib/config.ts`, checked again by the database). The buyer ticks it at checkout, the quote adds a line "Express delivery (24 hours)", the order is due in 24 hours, and the price counts as the seller's money (the fee is taken on product plus express, `baseCents`). Not offered for as-is downloads, which are delivered at once.
- **Reviews** (migration 0023, `lib/reviews.ts`): only the buyer of an accepted product order, one per order, 1 to 5 stars and a note without contact details or links. Written by the server only. Real ratings replace the made-up starter ones as soon as a listing has one. Product JSON-LD is always output; `AggregateRating` and `Review` only from real reviews (`components/JsonLd.tsx` is the one place allowed to use `dangerouslySetInnerHTML`, and it neutralises every `<`).
- **Abuse reports** (migration 0024, `lib/abuse.ts`): each reporter counts once (account, or a hash of the address). Three different VERIFIED reporters in 7 days (migration 0030: a verified-email account, or a buyer who paid for that listing; anonymous and throwaway-account reports are saved and alert the admins but do not count, so a competitor cannot pause a listing with fake accounts) pause the listing until an admin looks; the admin can suspend, dismiss, or put the site back. Five reports an hour per address at most.
- **Your data and cookies** (migration 0025, `lib/privacy.ts`): cookie notice (only needed cookies, no advertising or tracking, one button), a downloadable JSON copy of your own data, and an account deletion request that an admin processes. Processing anonymises (name, payout details, developer profile, notifications, question text, sign-in renamed and locked) and is refused while an order, a dispute or a payout is open. Payments, orders, the ledger, the audit log and the download log are kept without a link to a named person; the Privacy page says so.
- **Listing scan** (migration 0026, `lib/scan`): when a listing is submitted it fetches the seller's private file link (https, public addresses only, 50 MB), opens zips safely, and flags a test virus, Windows or Linux programs, a few well-known tricks, pasted secrets (keys, private keys, a service_role JWT), a missing licence file, the same file or 60%+ the same words as another listing, and a demo link that does not open. Local heuristics only, labelled as such; a real scanner plugs in behind `MalwareScanner`. It only adds flags: an admin still decides and opens digital files in a sandbox. File versions change only when the file's hash changes.
- **Domain renewal reminders** (`lib/orders/domains.ts`): 30, 7 and 1 days before a domain we registered expires, once each, from the scheduled job.
- **Developers' own trial package** (migration 0027): price from $5 to $150, 3 to 5 days, optional credit toward a full job. Blank means a price worked out from Basic. Products do not have trial packages: custom work is the developers' job, products are fixed templates.
- **Order chat** (migration 0028, `lib/chat.ts`): buyer and seller of a paid order; the server filter, a rate limit (20 a minute), strikes, and the new-message notification (once an hour per order and side). Polling every 4 seconds plus Supabase Realtime for signed-in people. Messages are written only by the server. Chat closes with the order (cancel, refund, paid out).
- **Free site-ideas tool** (migration 0029, `/tools/site-ideas`, `lib/tools`): 5 runs a day per visitor counted by cookie AND address, Turnstile, answers saved 30 days (a repeat is free and does not count), a monthly token budget switch (`AI_MONTHLY_TOKEN_BUDGET`, default 2,000,000, 0 = off), and every answer from the model is checked before it is shown (a name that is not a safe domain name is refused). Until a real model and key exist, `LocalAiProvider` answers from templates in the same JSON shape; domain availability shows "Check availability" until a real registrar is connected.
- **Category pages** (`/websites/[category]`, `/templates/[category]`, `lib/seo`): each category has its own written text, FAQ and structured data; a page exists only with at least three real products, and the sitemap and the links between categories follow the same rule.
- **Still not built, and why**: real payments (D1), KYC (D4), Google login and phone OTP (need provider keys and the owner's choice), a real email provider (key), AI features that need a real model (listing screening by AI, marketing kit, Solution Finder, paid content and SEO add-on), a real registrar (D3), automatic deployment (D5), the MDX blog structure.
- Migrations to apply, in order: 0015 to 0029.
- **Express fee policy (decided October 2026):** the 15% fee applies to the product price AND the express add-on, like the big marketplaces that take a commission on extras too. The seller keeps 85% of both. Domain, hosting and AI add-on prices are pass-through and carry no fee. Test: `tests/unit/express.test.ts`. Change it only in `lib/orders/machine.ts` (`baseCents`).
- **Malware scan before launch (launch blocker):** the scanner today is the local heuristics (`lib/scan/engine.ts`, name `local`). Before launch a real scanner (ClamAV or VirusTotal) must sit behind `MalwareScanner` and `SCAN_REQUIRE_REAL=1` must be set: then `decideListing` refuses to approve a listing with files for buyers unless a non-local scanner scanned it. Known malware always blocks approval. Tests: `approvalBlock` in `tests/unit/scan.test.ts`.
- **Dashboards show only real data:** buyer and seller dashboards read the person's own orders, ledger balances, listings and payouts (`lib/dashboard.ts`); a new account sees empty states, never a made-up name or sum.
- **Abuse hardening (migration 0031, `lib/guard.ts`, `/dashboard/admin/security`):** every write that can be spammed (sign up, sign in, order, list, hire, create a developer profile, open a dispute, send extra work) first calls `guard(action)`. Numbers live in `CONFIG.limits`: per person and per connection per window, a lower per-person limit for an account younger than 7 days, an alert when 4 accounts share a connection or device in a day, an alert when one connection is refused 10 times in an hour. The connection and the device (random id in the `lb_dev` cookie, set by the proxy) are stored only as salted hashes (`GUARD_SALT`) in `security_events` and purged after 90 days (daily job). Admins see shared connections and devices, refused connections and active blocks, and can block or lift a connection or device with a reason that goes in the audit log; banning one account stays on the Accounts page. A blocked connection or device gets a plain 403 on every guarded action. Addresses on this computer or a private network are never limited as a group (tests, local server). Limits are counted in memory (one server); move to Redis or Upstash when there are several. The privacy page mentions the device cookie. Chat, questions, reports, downloads and the free tool keep their own, older limits.
- **Risk tools (migration 0032, `/dashboard/admin/risk`):** (1) daily counters (`lib/metrics.ts`) for new accounts, orders, disputes, refunds, abuse reports and failed payments, bumped where each happens; a day at least 3 times the average of the 7 days before it, and at least the minimum in `CONFIG.risk`, alerts the admins once a day per metric (daily job). (2) Emergency switch `pause_new_buyer_checkout` (`lib/switches.ts`): signed-out visitors and accounts under 7 days cannot create an order or hire request while it is on (503 with a plain message); older accounts are not affected; every flip is audited. (3) Orders held for a safety check (`lib/holds.ts`, `order_holds`): a real (not demo) paid order from a flagged buyer, or from an account under 7 days paying $100 or more, waits before the seller can deliver and before any file or download link is released; the money stays in escrow; the admin releases it or cancels it (refund from escrow). It is a side table, not an order state, so the state machine is unchanged. (4) One-click clean-up (`lib/clean.ts`): ban an account for good and delete the reviews and abuse reports it wrote, or delete one review; refused for an account with a paid order; orders, chat, downloads and security events are never deleted (evidence). (5) The terms have a section on fake accounts, fraud and compensation, tagged [LAWYER REVIEW]. Not built: blocking a card (needs a real payment provider, D1), real Turnstile keys, Cloudflare in front, a second payment provider, the attack budget, lawyer notices.

- **Held orders and the delivery timer:** while an order waits for a safety check no timer runs (`tick` and the reminders skip it, so it cannot go overdue), the seller is told "waiting, do not start" instead of "start now" (`order_held`), the buyer sees a notice on the order page, the seller dashboard shows "Paused". On release the delivery deadline moves later by the time the order was held, so the seller keeps the time they had left, and the seller is told to start (`order_hold_decided`). The admins get a dedicated alert (`order_hold_alert`, in-app and email through the email provider) as soon as an order is held. The hold decision is made before anybody is notified of the payment (`beforeNotify` in `lib/orders/service.ts`). In a demo (no database) nobody counts as a new account unless a test says so.
- **Ledger risk rules (migration 0033):** (1) Seller reserve (`lib/reserve.ts`, `CONFIG.reserve`): when the payout hold ends, a share of the seller's money goes to `seller_reserve` instead of `seller_available`, and is let go `days` later (the scheduled job). The default is OFF (0 percent, 0 days) because the numbers are the owner's decision; an admin can set a rule for one seller on the Risk page (percent 0 to 100, days 0 to 180, audited). The weekly payout pays the available money only: an order's payout is its earnings less the part still in reserve, and a released reserve goes into the seller's next payout. (2) Claw-back and debt: money taken back from a seller (a refund after the payout hold, a dispute fee) comes out of pending, then reserve, then available, and what those cannot cover becomes `seller_debt` (the seller owes it; shown on their dashboard). New earnings pay the debt off first (`debt-settle:<order>` when an order is accepted). No ledger account other than debt can go below zero, in code and in the database function. (3) Dispute record: every decided dispute stores the reason, the decision (outcome), who was at fault (`liability`: seller, buyer_fraud, platform) and the fee the dispute cost (`fee_cents`, entered by the admin; no amount is assumed). When the seller is at fault the fee is taken from the seller automatically (`dispute-fee:<dispute>`, once); when the buyer is at fault (fraud) the buyer is flagged so their next orders are held; when it is us or nobody the fee is only recorded. Not decided by me: the reserve numbers and the dispute fee amount (they depend on the fee structure and the payment provider, decisions D1 and the owner's).
- **Accept consent and the evidence file (migration 0034, `lib/consent.ts`, `lib/evidence.ts`):** a buyer accepts an order only with the box ticked (`lib/consentText.ts`, with a version; the server refuses an accept without `consent: true`, 400). Each click is written to the append-only `order_consents` (time, user, connection address, browser, hashed device, version of the words). The address and browser are kept as they are, not hashed, because it is evidence for a dispute or chargeback; the privacy page says so, and the buyer's data export includes it. An order accepted by the timer has no click, and the evidence file says so. One click makes the evidence PDF (`/api/orders/<id>/evidence`, and `/api/demo/orders/<id>/evidence` for the buyer in a demo): order and timeline, every file delivery with time, address and file hash, the chat, the certificate fingerprint, the acceptance, and any dispute with its evidence and outcome, plus a fingerprint of the content. The buyer, the seller and the admin can download it; the admin sees full addresses (and needs the authenticator code, each download is audited), the parties see them with the last part hidden. [LAWYER REVIEW] before it is sent to a court or a payment provider.
- **Email blocklist and chargeback ban (migration 0035):** an admin can block an email address on the Security page; only a hash of its normal form is stored (lower case, no +tag, no dots in a Gmail name, googlemail.com is gmail.com), and a blocked address is refused at sign-up and sign-in. Removing a fake account blocks its email too. A lost chargeback arrives as the payment event `chargeback.lost` (the provider adapter maps its own event to it; no provider is assumed): the order's buyer is banned for good (`profiles.banned`, `ban_reason = 'chargeback'`, sign-in refused, email blocked), the event is audited, counted in the daily refunds, and the admins are alerted. That ban cannot be lifted from the Accounts page. NOT automatic: the money. Whether the seller loses the order's earnings, and who pays the chargeback fee, is the owner's decision (D1 and the fee structure); until then an admin decides it in Disputes with the liability and fee fields. Rate limits, the lower limits for new accounts and the connection and device blocklist were already built (abuse hardening).
- **Brand (decided by the owner, October 2026):** the product is called **SellOnBay**, on **sellonbay.com** (`lib/brand.ts`; support address `support@sellonbay.com` unless `NEXT_PUBLIC_BRAND_EMAIL` says otherwise: the mailbox must exist before launch). Everything visible was renamed (pages, emails, legal drafts, the evidence and certificate PDFs, docs); the webhook signature header is now `sellonbay-signature`. Also renamed while there are no real customers yet (it would break stored links later): the package name and the download-link signing prefix (`sellonbay-delivery:`), the dev-only hash salt. - **A real malware scanner: options, effort, waiting for the owner's decision.** Today `MalwareScanner` (`lib/scan/index.ts`) has only the local heuristics. To go live, write ONE class that implements it and put it in `defaultDeps.scanner`; set `SCAN_REQUIRE_REAL=1`. Options: (a) **ClamAV** (`clamd` over a socket): free software, files never leave our server, but we must run and update a server for it (not possible on a plain serverless host; about 1 to 2 days to build, plus keeping a small server running and its signatures fresh); it finds known malware, not clever new scripts. (b) **VirusTotal** (API): no server of our own, many engines, about half a day to build; but the file is uploaded to a third party (a seller's private files become visible to their customers, a privacy and contract question), the free plan is rate limited and not for commercial use, a paid plan costs money per request, and a big file needs a special upload URL. (c) **A paid scanning API** (for example a cloud antivirus service): similar effort to VirusTotal with a commercial licence; check the price and the data terms. For a marketplace with many files the usual choice is ClamAV on a small server plus VirusTotal only for hashes (looking a file up by its SHA-256 without uploading it). None of this finds a script that is harmful in a new way: a human review in a sandbox stays required for scripts and plugins.
